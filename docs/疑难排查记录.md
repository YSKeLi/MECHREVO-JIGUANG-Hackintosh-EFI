## 0. 排查方法论

### 0.1 不要靠"看起来像"

**教训**：判断显卡模式时，最初用"`ioreg` 里有没有 `IGPU@2` 字符串"来判断是否混合模式，结论反复出错。

正确做法是**看内屏归谁**：

```bash
ioreg -l -w0 | grep 'IODisplayPrefsKey" ='
```

输出路径前缀决定归属：

| 路径前缀 | 含义 |
|---|---|
| `.../IGPU@2-...` | 内屏由核显驱动（混合模式生效） |
| `.../PEGP@0-...` | 内屏由独显驱动（独显直连或回落到独显） |

**为什么不能看 `IGPU@2` 存在与否**：独显直连模式下，有些 BIOS 仍然枚举核显节点，但面板并不归它。字符串匹配会把"枚举"误判成"驱动"。

### 0.2 `log show --boot` 不可靠

本机 `log show --boot` 谓词经常返回空或错误范围。改用**时间窗口 + 按分钟分桶**：

```bash
log show --start '2026-11-05 09:30:00' --end '2026-11-05 10:00:00' \
  | awk '{print $2}' | cut -d: -f1,2 | sort | uniq -c
```

一次性导出到文件再分析，比反复查询快得多：

```bash
log show --start '...' --end '...' > /tmp/win.log   # 可能上百万行
awk '/AUX.*Time out/ {m=substr($2,1,5); c[m]++} END {for (k in c) print k, c[k]}' /tmp/win.log
```

### 0.3 改配置必须先校验

用 Python `plistlib` 修改，写临时文件，`plutil -lint` 通过后才覆盖：

```python
import plistlib, shutil, subprocess
shutil.copy('config.plist', 'config.plist.bak')
d = plistlib.load(open('config.plist','rb'))
d['Kernel']['Add'][i]['Enabled'] = False
plistlib.dump(d, open('/tmp/c.plist','wb'))
subprocess.run(['plutil','-lint','/tmp/c.plist'], check=True)
shutil.move('/tmp/c.plist','config.plist')
```

### 0.4 日志里"打印后执行"会骗人

某条错误日志往往是**动作执行前**打印的，NOP 掉动作后日志依然存在。

**例子**：

```
[IGFB][WARN] EFI should not enable AUX0 power well - overriding
```

这条日志在"关闭 AUX 电源井"的函数调用**之前**打印。把关闭动作 NOP 掉后，日志照样出现——一度误判"补丁没生效"，实际已经生效。

**验证方法**：反汇编确认调用点顺序，看日志打印和实际操作谁在前。

## 1. AuxKC 与 KDK（最大的坑）

### 1.1 现象

更新 NVIDIA 驱动到 2.7.1 后，重启无法进入系统。日志：

```
kernelmanagerd: No fileset UUID for auxKC, error: NSPOSIXErrorDomain Code=2
kernelmanagerd: Img4 error: format neither im4p nor img4 (3)
kernelmanagerd: error: tried to insert an invalid codeful kernel extension
    in the restricted lookup table:
    Kext com.nullmoth.NVRMAGDC v2.7.1 ...
    Kext com.nullmoth.NMXAudio v1.0.0 ...
    Kext org.voodoo.driver.VoodooHDA v3.0.2 ...
    Kext com.apple.driver.AppleIntelTGLGraphicsFramebuffer v16.0.0 ...
    Kext org.b00t0x.AppleIntelTGLCompat v0.7.0 ...
```

`WindowServer` 触发 watchdog timeout（`termination: monitoring timed out for service`），卡在登录界面，只能远程桌面进入。

### 1.2 排查过程

**第一步：先怀疑配置，而不是驱动。**

对比更新前后的备份，发现 config 没有实质变化。

**第二步：看驱动版本。**

```bash
kmutil showloaded | grep nullmoth
# 显示仍是 2.6.6 —— 说明更新没装成功，或者装完又回滚了
```

但 `/Library/Extensions` 里的 kext 时间戳是新的 → **文件被换了，但内核集合没跟着重建**。

**第三步：重点看 AuxKC。**

```bash
kmutil inspect | grep 'auxiliary kext collection'
# auxiliary kext collection at /Library/KernelCollections/...   ← 没有 UUID！
```

对照正常状态（后来修好后）：

```
auxiliary kext collection at /Library/KernelCollections/AuxiliaryKernelExtensions.kc (36939410-DD61-62AF-89F5-008F7F1A81BF)
                                                                       ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
                                                                       这一串就是 fileset UUID
```

### 1.3 根因

macOS 13+ 要求所有第三方 kext 打包进 **AuxKC** 并**签名封存**。重建 AuxKC 需要 **KDK**（Kernel Development Kit，含内核符号和开发头文件）。

没有 KDK 时，重建只能退化为：

```bash
kmutil create -n aux -x -z -V release -r /Library/Extensions \
  --allow-missing-kdk -p <kext>... -B BootKernelExtensions.kc \
  -S SystemKernelExtensions.kc -A <out> --no-authentication
```

`--no-authentication` 生成的镜像**没有 fileset UUID**，属于非法集合。内核在受限查找表里插入 kext 时全部失败 → 所有 codeful kext 失效 → 系统起不来。

### 1.4 解决

```bash
# 1. 下载对应 build 的 KDK（社区镜像，不需要开发者账号）
#    https://github.com/dortania/KdkSupportPkg/releases/tag/25G332
#    Kernel_Debug_Kit_26.7.2_build_25G332.dmg  (1126 MB)

# 2. 安装
hdiutil attach Kernel_Debug_Kit_26.7.2_build_25G332.dmg
sudo installer -pkg "/Volumes/Kernel Debug Kit/KernelDebugKit.pkg" -target /
hdiutil detach "/Volumes/Kernel Debug Kit"

# 3. 验证
ls /Library/Developer/KDKs/
# → KDK_26.7.2_25G332.kdk

# 4. 重建并确认 UUID
sudo kmutil rebuild
kmutil inspect | grep 'auxiliary kext collection'
```

装好 KDK 后，同一次 2.7.1 更新**一次成功**，且 AuxKC 有了合法 UUID。

### 1.5 弯路与误判

| 误判 | 真相 |
|---|---|
| "驱动 2.7.1 本身有 bug" | 驱动没问题，是 KC 重建失败 |
| "AuxKC 损坏是 WEX 造成的" | 与 WEX 无关，缺 KDK 时谁重建都会坏 |
| "回滚删掉 NMXAudio 就好了" | 只是去掉了一个不一致项，视频驱动四个 kext 依然不匹配 |

**关键认知**：`No fileset UUID` 和 `Img4 error` 这两条错误，在**能正常启动的配置里也会偶尔出现**（实测正常启动 4–6 次，失败启动 0 次）。所以不能只看这两条，要看**是否伴随大量 `invalid codeful kernel extension`**。

### 1.6 经验

1. macOS 13+ 装任何第三方 kext 前，**先确认 KDK 已安装**
2. `kmutil inspect | grep 'auxiliary kext collection'` 是判断 KC 是否合法的**唯一可靠方法**
3. 更新驱动前，备份 `/Library/KernelCollections/AuxiliaryKernelExtensions.kc`

## 2. 核显接入：显存、电源井、面板

这一节记录让 UHD 770 在混合模式下拉起显示链路时遇到的三个独立问题。

### 2.1 DVMT 显存计算错误

**现象**：

```
AppleIntelFramebufferController: Insufficient stolen memory
AppleIntelFramebufferController: Can't create cursor memory
IGStolenMemoryPool = 0
```

随后偶发 panic：

```
IGAccelTask::withOptions → IOAccelTask::release
CR2=0xc78  RDI=0x0
```

**排查**：

固件 GGC 寄存器 = `0xFEC7`，高字节 `0xFE` → 预分配 **60 MB** 显存。

Apple 的 `FBMemMgr_Init()` 用如下指令计算：

```asm
0x42DA1: C1 E0 11              shll $0x11, %eax        ; eax = guc * 0x20000
0x42DA4: 25 00 00 00 FE        andl $0xFE000000, %eax  ; 只保留高 7 位
0x42DA9: 41 89 87 E4 0D 00 00  movl %eax, 0xde4(%r15)
```

这个公式假设显存是 32 MB 的整数倍。本机 60 MB 不满足，计算出的值与实际不符。

**方案**：直接改二进制，把 60 MB 写死：

```asm
0x42DA1: 90 90 90              nop × 3
0x42DA4: B8 00 00 C0 03        movl $0x03C00000, %eax   ; 60 MB
```

**注意**：WEX 运行时也会打这个补丁（对应属性 `TGLStolenMemoryApplied`），但实测静态补丁更可控——因为运行时补丁依赖 kext 被正确加载，而 AuxKC 非法时全部失效。

**验证**：

```bash
# 检查补丁是否在
xxd -s 0x42DA1 -l 8 /Library/Extensions/AppleIntelTGLGraphicsFramebuffer.kext/Contents/MacOS/AppleIntelTGLGraphicsFramebuffer
# 期望：9090 90b8 0000 c003
```

### 2.2 AUX 电源井被固件关闭

**现象**：

```
[IGFB][WARN] EFI should not enable AUX0 power well - overriding
```

**排查**：`AppleIntelPowerWell::init()` 会遍历电源井，把"固件已开启但驱动认为不该开"的 AUX/DDI 电源井**强行关闭**。

反汇编定位到关闭调用：

```
0x5a471: E8 94 09 00 00    call disablePowerWellAux
```

**方案**：替换为 5 个 NOP。

```asm
0x5a471: 90 90 90 90 90
```

**重要**：如 [0.4](#04-日志里打印后执行会骗人) 所述，那条日志依然会出现，因为它打印在关闭动作之前。**不能以日志消失作为补丁生效的判据。**

### 2.3 面板电源补丁（失败，已回滚）

**目标**：解决"开机内屏黑，休眠唤醒后才亮"。

**思路**：`hwSetPanelPower` 里有"关"和"开"两个分支，把"关"分支入口改成直接返回。

**第一次改错了**：

把 `0x486e3` 处的 `jne` 当成 6 字节指令（实际是 2 字节 `75 68`），把条件跳转改成了**无条件跳转**，导致"开面板"路径也被跳过。

**修正**：

```asm
0x486e3: 31 C0              xor %eax, %eax
0x486e5: E9 D4 03 00 00     jmp epilogue
```

7 字节，正好覆盖原来的 `incq` 指令。

**结果**：逻辑正确了，但核显启动仍然异常，最终**全部回滚**，`hwSetPanelPower` 保持原样。

**复盘**：面板电源是核显显示链路的关键路径，改它风险很高。后来发现问题的本质不是"电源没开"，而是 **AUX 读不到面板**（见第 4 节），方向从一开始就偏了。

### 2.4 静态改二进制的流程

```bash
# 1. 备份
cp -p AppleIntelTGLGraphicsFramebuffer AppleIntelTGLGraphicsFramebuffer.orig

# 2. 用 Python 打补丁（不要用 sed，二进制不安全）
python3 -c "
import pathlib
p = pathlib.Path('AppleIntelTGLGraphicsFramebuffer')
b = bytearray(p.read_bytes())
b[0x42DA1:0x42DA4] = bytes([0x90,0x90,0x90])
b[0x42DA4:0x42DA9] = bytes([0xB8,0x00,0x00,0xC0,0x03])
p.write_bytes(bytes(b))
"

# 3. 重新签名（ad-hoc）
codesign -f -s - AppleIntelTGLGraphicsFramebuffer.kext

# 4. 重建 AuxKC（必须！否则签名/内容不匹配）
sudo kmutil rebuild
```

## 3. IONDRVFramebuffer 抢占核显

### 3.1 现象

混合模式下核显驱动不启动，`ioreg` 显示：

```
IGPU@2
└── IONDRVFramebuffer     ← 通用 NDRV 驱动占住了核显
```

### 3.2 原因分析

两个驱动的匹配规则：

**`IONDRVFramebuffer`**（Apple 通用驱动）：

```
IONameMatch = "display"                     IOProbeScore = 20000
IOPCIClassMatch = 0x03000000 & 0xff000000   （兜底规则，匹配任何显示控制器）
```

**`AppleIntelFramebufferController`**：

```
IOPCIPrimaryMatch = 0x46888086 ...          IOProbeScore = 80000
```

分数更高，但它在 **AuxKC 里加载更晚**。IOKit 的 probe 顺序由加载时间决定——**谁先 probe 到谁赢**。

### 3.3 三种尝试，全部失败

| 方案 | 具体做法 | 结果 |
|---|---|---|
| Block 策略 | `Kernel → Block` 中 `IONDRVSupport` 的 `Strategy` 从 `Exclude` 改成 `Disable` | **无效**，IONDRVSupport 照常加载 |
| 改 IOName | iGPU 的 DeviceProperties 加 `IOName = "IGPU"` | 属性写入了，IONDRV 仍匹配（因为有 class 兜底规则） |
| 静态改二进制 | 把 `AppleIntelFramebufferController` 的 score 改了 | 破坏签名 → AuxKC 非法 → 开不了机 |

### 3.4 为什么 Block 无效

`Kernel → Block` 只对 **OpenCore 注入的 kext** 生效（通过修改 prelinked kernel 或阻止注入）。
`com.apple.iokit.IONDRVSupport` 位于**系统内核集合**（SystemKC）里，Block 拦不住。

同理 `Strategy = Exclude` 和 `Disable` 都不行——这个认知花了几轮重启才确认。

### 3.5 最终状态

放弃这条路。真正的问题在 [第 4 节](#4-混合模式内屏从-aux-超时到-doze-时长)——即使核显驱动加载了，AUX 读不到面板也没用。

## 4. 混合模式内屏：从 AUX 超时到 Doze 时长

这一节的结论经历过多次修正，把完整过程留下来，避免重复踩坑。

### 4.1 最初的现象

混合模式 + 接外屏，开机后内屏只有背光。跑 `pmset displaysleepnow` 再唤醒，日志刷 `AUX Time out`：

```
[IGFB][ERROR][AUX] ddi = 0 Time out: 0x5d40023f   /   0x8d40023f
[IGFB][ERROR][LINK_TRAINING] Phase 1 of link training failed
[IGFB][ERROR][DISPLAY] FB0 is not enabled
```

一度以为是 AUX 通道彻底坏了。

### 4.2 第一个误判：以为"唤醒必然重新训练链路"

当时把每次启动按 boot 分组统计，看到成功的那次没有 `LINK_TRAINING` 错误行，失败的有 16 行，于是推测"成功那次跳过了训练"。

**这个理解是错的**：AUX 成功时不会打日志，所以"没有错误行"不代表"没做训练"。

### 4.3 关键发现：Doze 时长

把历史上每一次 Doze→Wake 的**间隔**算出来，规律立刻出现：

| Doze 持续 | 结果 | 时间 |
|---|---|---|
| **1.0 秒** | ✅ 成功 | 11-07 14:07 |
| **1.6 秒** | ✅ 成功 | 11-06 15:31 |
| 5.8 秒 | ❌ 失败 | 11-07 12:09 |
| 20.0 秒 | ❌ 失败 | 11-07 12:08 |
| 42.2 秒 | ❌ 失败 | 11-07 12:26 |
| 57.1 秒 | ❌ 失败 + DBUF 超时 | 11-07 13:36 |
| 57.8 秒 | ❌ 失败 + DBUF 超时 | 11-07 13:50 |

**阈值在 2～5 秒之间。**

### 4.4 机制

```
短 Doze（≤2 秒）
  面板电源没真正断，eDP 链路保持
  → 唤醒不需要重新训练 → 直接点亮 ✅

长 Doze（>5 秒）
  面板深度断电（连 DBUF 显示缓冲电源井都掉电，日志出现 "DBUF 2 power up timeout"）
  → 唤醒必须重新训练链路
  → 训练要读写面板 DPCD，走 AUX
  → AUX 在这台机器上不通 → 超时 → Phase 1 失败
  → 驱动通知 AGDC 把显示下线 → FB0 is not enabled → 只能重启
```

所以 AUX 本身不是"彻底坏"，而是在面板深度断电后无法工作。

### 4.5 为什么会踩进长 Doze

我当时给的操作是：

```bash
pmset displaysleepnow
sleep 3
caffeinate -u -t 2
```

问题出在 **`caffeinate -u` 不会唤醒已经睡着的显示器** —— 它只是"阻止系统休眠"。于是屏幕一直黑着，直到用户手动碰键盘，间隔被拉到几十秒 → 必然失败。

而 11-06 成功那次，用户跑完 `pmset displaysleepnow` 后很快就碰了键盘，间隔只有 **1.6 秒**。

### 4.6 正确的操作

```bash
pmset displaysleepnow
```

**然后 2 秒内按一下空格键。**

或直接用脚本（内含模拟按键 + 结果自检）：

```bash
bash scripts/激活内屏.sh
```

### 4.7 成功与失败的日志对照

**成功**（间隔 1.0 秒）：

```
14:07:25.084  FB0: power state transition Wake --> Doze
14:07:26.040  FB0: power state transition Doze --> Wake
14:07:26.474  FB0: Complete modeset
              （无 AUX 超时、无训练失败、无 FB0 禁用）
```

**失败**（间隔 57.8 秒）：

```
13:49:43.596  FB0: power state transition Wake --> Doze
13:50:41.401  FB0: power state transition Doze --> Wake
13:50:41      [ERROR][DISPLAY] DBUF 2 power up timeout
13:50:41      [ERROR][AUX] ddi = 0 Time out: 0x8d40023f
13:50:42      [ERROR][LINK_TRAINING] writeAUX failed / readAUX failed
13:50:42      [ERROR][LINK_TRAINING] Phase 1 of link training failed
13:50:43      [ERROR][DISPLAY] FB0 is not enabled
```

### 4.8 排除掉的假设（都试过，都不是原因）

| 假设 | 验证方式 | 结果 |
|---|---|---|
| NVIDIA 2.7.1 与核显冲突 | 降级到 2.6.6 | ❌ 无效 |
| 二进制补丁（AUX 电源井 NOP）导致 | 哈希对比，与 11-04 完全一致 | ❌ 没变过 |
| 内核集合缺 `--kernel` 符号解析 | 用 1401 参数重建 | ❌ 无效 |
| 音频驱动（VoodooHDA vs NMXAudio） | 两种都试 | ❌ 都失败 |
| 内核集合构建方式 | 4 种不同构建 | ❌ 无效 |
| 冷启动能重置状态 | 断电冷启动 | ❌ 无效 |
| 改分辨率能触发初始化 | `CGDisplaySetDisplayMode` | ❌ 不触发任何驱动动作 |

**最终是"Doze 时长"这一个变量解释了全部现象。**

### 4.9 经验

1. **日志里没有错误 ≠ 没执行** —— AUX 成功时是静默的
2. **时间间隔是重要的隐藏变量**，统计事件时要算间隔，不能只数次数
3. `caffeinate -u` 不是唤醒屏幕的手段
4. 失败一次后要 `FB0 is not enabled` 消失必须重启，重试前先重启

## 5. USB 端口映射

### 5.1 现象

U 盘插上完全不被识别（`diskutil list external` 为空），同样的 U 盘在 Windows 下正常。

### 5.2 排查

```bash
# 看控制器暴露的端口
ioreg -w0 -l | grep -E 'AppleUSB(20|30)XHCIPort'
```

结果：

```
15 个 AppleUSB20XHCIPort  （USB 2.0 端口）
 1 个 AppleUSB30XHCIPort  （USB 3.0 端口）
```

**问题**：USB 3.0 端口只识别出 1 个。原来用的 `UTBDefault.kext` 只是类绑定，**没有任何端口映射**。

### 5.3 方案

用 `USBToolBox` + 完整的 `UTBMap.kext`（10 个端口）：

| 端口号 | 类型 | 名称 |
|---|---|---|
| 1, 5, 14 | 255（内置） | HS01, HS04, HS06 |
| 3, 4 | 9（Type-C） | HS02, HS03 |
| 9 | 3（USB3-A） | HS05 |
| 17 | 255 | SS01 |
| 19, 20 | 9（Type-C） | SS02, SS03 |
| **25** | **3（USB3-A）** | **SS04** |

**关键点**：

1. `port-count` 必须 ≥ 最大端口号（这里是 25）
2. 在 `Kernel → Add` 里，`USBToolBox.kext` 必须排在 `UTBMap.kext` **前面**
3. `USBToolBox` 版本需 ≥ 1.0.0（本机 1.2.0）

### 5.4 验证

```bash
ioreg -w0 -l | grep -oE '\+-o (HS|SS)[0-9]+'
# 期望：HS01..HS06 + SS01..SS04
```

重启后 U 盘（Kingston DataTraveler 3.0，61.9 GB）成功识别为 `disk4`。

## 6. 音频驱动冲突

### 6.1 现象

升级 NVIDIA 驱动到 2.7.1 后，音频设备完全消失：

```bash
system_profiler SPAudioDataType
# Audio: Devices:      ← 空的
osascript -e 'output volume of (get volume settings)'
# → missing value
```

### 6.2 分析

`kmutil showloaded` 显示两个音频驱动同时在跑：

```
com.nullmoth.NMXAudio (1.0.0)        ← 2.7 新装（macOS 26 不自带 HD Audio）
org.voodoo.driver.VoodooHDA (3.0.2)  ← 旧方案
```

两者抢同一个 HDA 控制器，结果**都没有生成输出设备**。

### 6.3 方案

2.7 的 `NMXAudio` 是官方为 macOS 26 做的，应该由它接管：

```bash
# 1. 移走旧的
sudo mkdir -p /Library/Extensions-disabled
sudo mv /Library/Extensions/VoodooHDA.kext /Library/Extensions-disabled/

# 2. 重建 AuxKC（现在有 KDK，能成功）
sudo kmutil rebuild

# 3. 确认已从集合中移除
kmutil inspect | grep -ci voodoo    # 期望 0
```

### 6.4 结果

```
Conexant (0x1f87) (Right Analog)      2 声道
Conexant (0x1f87) (Internal Analog)   2 声道
NVIDIA (0x00ad) (HDMI/DP 8ch)         2 声道
```

4 个输出设备，板载模拟 + HDMI/DP 音频都正常。

## 7. 显示归属的判断（方法论教训）

### 7.1 错误判断

最初判断"是否混合模式"用的是：

```bash
ioreg -w0 -l -p IOService | grep -c 'IGPU@[0-9a-f]'
```

结果一直把独显直连误判成混合模式——因为**独显直连时核显节点依然被枚举**。

### 7.2 正确判断

```bash
ioreg -l -w0 | grep 'IODisplayPrefsKey" =' | sed 's/.*= //'
```

看完整路径：

```
IOService:/.../PC00@0/AppleACPIPCI/IGPU@2-9e5-d5e-...        ← 核显
IOService:/.../PC00@0/.../PEGP@0-2163-2437-...               ← 独显
```

**内屏的 `Connection Type: Internal` 出现在哪个 GPU 下面，就是哪块 GPU 在驱动内屏。**

### 7.3 辅助手段

`system_profiler` 更直观：

```bash
system_profiler SPDisplaysDataType
```

看 `Main Display: Yes` 和 `Connection Type: Internal` 挂在哪个 GPU 下。

### 7.4 教训

**永远用结构化数据（路径、树层级）判断，不要用字符串包含关系。**
字符串匹配会被"存在但未使用"的状态误导。

## 8. 其他问题

### 8.1 处理器名称显示错误

**现象**：关于本机显示 `24-Core Intel Xeon W` / `2.3 GHz`，但内核是正确的：

```bash
sysctl machdep.cpu.brand_string
# 13th Gen Intel(R) Core(TM) i7-13700HX
```

**三次尝试**：

| ProcessorType 值 | 结果 |
|---|---|
| `3841`（0x0F01，原来的值） | 显示 "24-Core Intel Xeon W"（错，但具体） |
| `0` | 显示 **"未知"**（更差） |
| `3841` + `revpatch=cpuname` + `revcpu=1` | ✅ 显示真实型号 |

**原理**：macOS 用 SMBIOS 处理器类型码查表。`0` 会落到 Unknown 分支。品牌串补丁由 `RestrictEvents` 的 `cpuname` 提供。

### 8.2 4K 硬解"看起来没有"

**误判**：早期测试 `VTIsHardwareDecodeSupported` 全部返回 false，以为没有硬解。

**真相**：**必须先在进程内创建 Metal 设备**，否则 VT 不会注册硬件解码器。

```swift
import VideoToolbox
import Metal

let dev = MTLCreateSystemDefaultDevice()   // ← 少了这行，结果全错
print(VTIsHardwareDecodeSupported(kCMVideoCodecType_HEVC))
```

建了 Metal 设备之后：

| 编码 | 结果 |
|---|---|
| HEVC (hvc1) | ✅ 支持 |
| H.264 (avc1) | ✅ 支持（2.7.1 上实测） |
| VP9 / AV1 / ProRes | ❌ 不支持 |

**实测性能**：

| 场景 | 帧率 |
|---|---|
| 4K HEVC 10bit 硬解 | 162 fps |
| 4K H.264 软解 | 26.4 fps |
| 1440p H.264 软解 | 78.4 fps |

### 8.3 Safari 为什么不走硬解

检查进程加载的库：

```bash
lsof -p $(pgrep -f 'com.apple.WebKit.GPU') | grep -iE 'nvdec|NVMTL'
```

**Safari 的 WebKit 进程完全不加载 `libnvdec_*.dylib`**，所以全程软解。

Chrome 则正常加载（`libnvdec` ×2、`NVMTL` ×8），GPU 进程 CPU 仅 20%。

**结论**：需要 4K 流畅就用 Chrome。

### 8.4 桌面卡顿的定性

**逐层排除**：

| 检查项 | 方法 | 结论 |
|---|---|---|
| CPU 频率 | 自写基准（单线程 1.07 G iter/s，8 线程扩展 9.6×） | 正常睿频 |
| 整机负载 | `top` | 24 线程 82% 空闲 |
| 热降频 | `powermetrics` | `CPU_Speed_Limit = 100` |
| 帧节奏 | CVDisplayLink 采样 | 180 fps，σ 0.34 ms，**0 掉帧** |
| WindowServer | 活动监视器 | 空闲 84–111%，卡顿时 130–200% |
| 拖窗口实测 | 计时器 | 75–77 fps，**12.5–13.0 ms CPU/帧** |

**结论**：**WindowServer 单核 CPU 受限**，不是配置问题。与上游 issue #356 报告的数字（13–14 ms/帧）一致。

试过 `debug.nvrmfb_flip_latch=2`，**无效**（longest completion wait 5803 µs vs 5813 µs，missed deadline 与 skipped 均为 0）。

### 8.5 ESP 挂载失败

`diskutil mount disk0s1` 报 `Volume on disk0s1 failed to mount`，但 `fsck_msdos` 检查正常。

**绕过方法**：

```bash
sudo mkdir -p "/Volumes/NO NAME"
sudo /sbin/mount_msdos /dev/disk0s1 "/Volumes/NO NAME"
```

卸载用 `diskutil unmount`。

### 8.6 `cp -R` 嵌套目录

```bash
cp -R src ./Existing.kext
# 结果：Existing.kext/src/...   ← 多了一层
```

**正确做法**：

```bash
rm -rf ./Existing.kext
cp -R src ./Existing.kext
```

## 9. 踩坑清单

### AuxKC / KDK

- [ ] 没有 KDK 时**绝不能**更新驱动
- [ ] `kmutil create --no-authentication` 生成的 KC 没有 fileset UUID，属于非法
- [ ] 判断 KC 合法性：`kmutil inspect | grep 'auxiliary kext collection'` 后面要带 UUID
- [ ] `No fileset UUID` / `Img4 error` 单独出现**不代表**出问题，要看是否伴随大量 `invalid codeful kernel extension`
- [ ] KDK 可从 `dortania/KdkSupportPkg` 获取，不需要开发者账号

### `Kernel → Block`

- [ ] `Strategy: Exclude` 对系统 KC 里的 kext 无效
- [ ] `Strategy: Disable` 同样无效
- [ ] Block 只能拦 OpenCore 注入的 kext

### 核显

- [ ] 运行时补丁依赖 kext 被正确加载；AuxKC 非法时全部失效
- [ ] 日志"打印后执行"，NOP 掉动作后日志仍然存在
- [ ] **开机时驱动跳过 eDP 链路训练**，所以内屏只有背光
- [ ] **Doze 时长是激活成败的唯一判据：≤2 秒成功，>5 秒必失败**
- [ ] `caffeinate -u` 不能唤醒屏幕，别拿它当唤醒手段
- [ ] `FB0 is not enabled` 出现后只能重启
- [ ] 改分辨率不会触发驱动重新初始化，只有电源状态转换会
- [ ] 核显驱动内屏**必须有第二个显示设备**（接外屏或用假负载）
- [ ] 混合模式内屏固定 60 Hz

### 判断方法

- [ ] 用 `IODisplayPrefsKey` 路径判断显示归属，**不要**用 `IGPU@2` 字符串
- [ ] `log show --boot` 本机不可靠，用时间窗口
- [ ] 大批量日志先导出到文件，再本地分析
- [ ] 不要在没有视觉反馈（远程桌面）时连续做显示模式操作

### 二进制补丁

- [ ] 补丁前备份原文件，记录偏移
- [ ] 用 Python 改字节，不要用 `sed`
- [ ] 改完必须 `codesign -f -s -` 重签
- [ ] 改完必须 `kmutil rebuild` 重建 KC
- [ ] 反汇编确认指令长度（`jne` 是 2 字节 `75 xx`，不是 6 字节）

### 硬件常识

- [ ] 关于本机里的 1536 MB 是**固定标称值**，不是真实显存
- [ ] 真实显存看 stolen memory（DVMT），由 GGC 寄存器高字节决定
- [ ] macOS 26 不再提供 HD Audio 驱动，必须有第三方方案
- [ ] 显示驱动重装会重置刷新率到 60 Hz
- [ ] Intel 网卡无 AWDL，AirDrop/接力不可用
